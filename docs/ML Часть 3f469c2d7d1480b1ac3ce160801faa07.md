# ML Часть

Мы делаем сервис для автоматической обработки аудио- и видеозаписей встреч, собеседований, интервью и т.д. Пользователь загружает файл через веб или мобильное приложение, основной backend сохраняет его и отправляет задачу в отдельный ML-микросервис.

Задача ML-части — принять аудио, распознать речь, получить таймкоды и спикеров, затем прогнать транскрипцию через LLM: исправить ошибки, сделать summary, выделить темы, ключевые тезисы, решения и задачи. В дальнейшем по готовой записи должен работать чат с ИИ.

ML-микросервис хотим сделать на Spring Boot как управляющий слой, а модели запускать через отдельные inference-runtime/worker'ы. Для speech-to-text рассматриваем WhisperX v3 или аналог, для LLM — Qwen или аналог.

Отдельная важная фича — автоматический выбор ML-пресета под железо. Сервис должен определять GPU, VRAM, CUDA и по этим параметрам выбирать размер моделей, precision и batch size. Если памяти не хватает — автоматически снижать пресет или уходить на CPU.

Основной backend не должен знать детали ML. Он просто создаёт job, получает jobId, следит за статусом и в конце забирает нормализованный результат.

## Примерный контракт

## 1. Общая схема

```
Frontend / Mobile
        ↓
   Main Backend
        ↓
    ML Backend
        ↓
 STT / LLM / AI
```

Frontend и Mobile напрямую с ML Backend не взаимодействуют.

Основной Backend отвечает за:

- пользователей;
- авторизацию;
- файлы;
- историю;
- папки;
- права доступа;
- хранение результатов.

ML Backend отвечает за:

- обработку аудио;
- распознавание речи;
- таймкоды;
- разделение по спикерам;
- исправление текста;
- суммаризацию;
- анализ;
- AI-чат.

# 2. Создание задачи обработки

## Request

```
POST /api/v1/ml/jobs
```

```
{
  "requestId": "7f95c2e4-...",
  "recordId": "f21d...",
  "file": {
    "url": "https://storage/.../audio.mp3",
    "name": "meeting.mp3",
    "contentType": "audio/mpeg"
  },
  "options": {
    "language": "auto",
    "diarization": true,
    "timestamps": true,
    "correction": true,
    "summary": true,
    "topics": true,
    "decisions": true,
    "tasks": true,
    "preset": "AUTO"
  }
}
```

`requestId` используется для идемпотентности.

Если Main Backend повторно отправит тот же запрос, ML Backend не должен создавать вторую задачу.

## Response

```
{
  "jobId": "ml-job-123",
  "recordId": "f21d...",
  "status": "QUEUED",
  "preset": "MEDIUM"
}
```

HTTP:

```
202 Accepted
```

COMPLETED

# 4. Получение статуса

```
GET /api/v1/ml/jobs/{jobId}
```

Response:

```
{
  "jobId": "ml-job-123",
  "recordId": "f21d...",
  "status": "TRANSCRIBING",
  "progress": 42,
  "stage": "SPEECH_TO_TEXT",
  "message": "Transcribing audio",
  "preset": "MEDIUM"
}
```

`progress` — от `0` до `100`.

# 6. Callback от ML Backend

Вместо постоянного polling лучше предусмотреть callback.

При создании задачи Main Backend передаёт:

```
{
  "callbackUrl": "https://backend/api/v1/internal/ml/callback"
}
```

После изменения состояния ML Backend отправляет:

```
POST /api/v1/internal/ml/callback
```

```
{
  "jobId": "ml-job-123",
  "recordId": "f21d...",
  "status": "COMPLETED",
  "progress": 100
}
```

После этого Main Backend запрашивает результат.

Либо ML Backend может сразу передать результат в callback.

# 10. Чат по записи

Основной Backend хранит историю чата, а ML Backend отвечает за генерацию ответа.

```
POST /api/v1/ml/chat
```

Request:

```
{
  "recordId": "f21d...",
  "question": "Какие решения были приняты?",
  "context": {
    "transcript": "...",
    "segments": []
  }
}
```

Лучше, если ML Backend умеет получать контекст записи самостоятельно по внутреннему идентификатору или из собственного временного хранилища.

Response:

```
{
  "answer": "Было принято решение перенести релиз...",
  "sources": [
    {
      "start": 560.2,
      "end": 590.7
    }
  ]
}
```

# 12. Авторизация между микросервисами

ML API не должен быть публичным.

Варианты:

- внутренний JWT;
- API key;
- mTLS;
- service-to-service token.
- grpc (?)

Например:

```
Authorization: Bearer <service-token>
```

Пользовательский JWT напрямую в ML Backend передавать необязательно.

ML Backend должен доверять только Main Backend.

---

# 13. Idempotency

При создании job Main Backend передаёт:

```
Idempotency-Key: 781d...
```

Если запрос был отправлен повторно из-за timeout, ML Backend возвращает существующий `jobId`.

Это защищает от двойной обработки одного аудио.

---

# 14. Correlation ID

Каждый запрос между сервисами должен содержать:

```
X-Correlation-Id: ...
```

Этот ID используется в логах:

```
Main Backend
↓
ML Backend
↓
STT
↓
LLM
```

Так можно отследить всю цепочку обработки одной записи.

# 16. Основной end-to-end сценарий

```
1. Пользователь загружает файл
              ↓
2. Main Backend сохраняет файл
              ↓
3. Main Backend создаёт record
              ↓
4. POST /ml/jobs
              ↓
5. ML Backend создаёт job
              ↓
6. Возвращает jobId
              ↓
7. ML Backend запускает обработку
              ↓
8. Main Backend получает статусы
              ↓
9. ML Backend завершает обработку
              ↓
10. Callback → Main Backend
              ↓
11. Main Backend получает результат
              ↓
12. Сохраняет результат в БД
              ↓
13. Web/Mobile получает данные
```

# Разделение ответственности

**Main Backend хранит бизнес-сущности:**

```
User
Record
Folder
Tag
Transcript
Analysis
ChatHistory
```

**ML Backend хранит технические сущности:**

```
MlJob
MlPreset
HardwareInfo
ProcessingStage
ModelInfo
ProcessingMetrics
```

ML Backend не должен знать про права пользователя, папки, UI или бизнес-логику приложения.

Main Backend, в свою очередь, не должен знать, каким конкретно способом ML Backend запускает Whisper, Qwen или другие модели.
